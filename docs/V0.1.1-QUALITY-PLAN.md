# 0.1.1 quality programme

Recorded 2026-09-05 from the maintainer's requested reviews. All items below
are accepted work to pursue. An unchecked item is not implemented or verified.
This record supplements ROADMAP.md; it does not mark existing milestones as
complete or change the project's platform, language, security or non-goals.

The maintainer subsequently specified an aggressive preference for adopting
new technology. Follow [TECHNOLOGY-DIRECTION.md](TECHNOLOGY-DIRECTION.md) when
choosing implementations; modern implementations are active work alongside
these fixes. All feature entries remain accepted, including work previously
described as optional or a later candidate. Validate semantics and evidence
before marking any entry complete.

Evidence levels: **reproduced** = executed on the current source;
**inspection** = a concrete code path, requiring targeted verification;
**audit** = a scenario/risk to investigate; **feature** = accepted product work
whose detailed behaviour still needs design. Performance changes require a
baseline and a measured result; an audit is not automatically a defect.

## Stage 2 — responsiveness and performance

- [x] P01 **inspection**: Replace main-thread blocking PTY writes with bounded,
  ordered, cancellable output; serialize user input and protocol replies.
  - Fixed 2026-09-07. `TerminalSession.write` was a synchronous
    `PTY.writeAll` on the calling (main) thread; measured on Darwin a pty's
    input side absorbs ~90–134 MB before `write(2)` stalls, and from there
    each write costs tens of ms and soon blocks indefinitely (a runaway
    child that stops reading, e.g. `yes`, gets there from ordinary typing
    alone). `write` now only enqueues onto a bounded FIFO
    (`PendingWrites`, head-indexed so draining is amortized O(1)) drained
    by one serial `writerQueue` in enqueue order; the parser's query
    replies take the same queue (`enqueueWrite`), which is what keeps
    replies ordered with respect to the keyboard input around them —
    previously the reader thread wrote replies synchronously and could
    interleave bytes with a main-thread write. Back-pressure: a backlog
    past `maxPendingWriteBytes` (4 MB) means the child is provably not
    reading, so new input is dropped rather than buffered without bound
    (the alternative is the UI freezing on a wedged child); a single chunk
    larger than the cap is still accepted while the backlog is under it, so
    a large paste goes through whenever the pipe drains at all. `stop()`
    discards everything pending; a drain parked in `write(2)` is released
    by `terminate()` (child death closes the replica → `EIO`) and then
    observes `stopped`. Files:
    `CortaTerminal/Sources/CortaTerminal/TerminalSession.swift` (queue,
    drain, `writerSink` test hook); `Corta/…` call sites needed no change
    (signature unchanged). Tests: `TerminalSessionWriteQueueTests` (5) —
    userInputAndProtocolRepliesKeepTheirEnqueueOrder (scripted
    `readerSource` feeds a DA1 query between two user writes; asserts the
    sink stream is input, reply, input), writeDoesNotBlockBehindAStalledWrite
    (gated sink parks the drain; the caller's next `write` returning at all
    is the assertion), stopDiscardsPendingWrites (queued bytes never reach
    the sink after stop; post-stop writes rejected),
    backlogBeyondTheCapIsDropped (7×1 MB against a parked drain; the
    seventh is dropped), queuedWritesReachTheChildInOrder (end-to-end FIFO
    through a real `/bin/cat`). Verified: `cd CortaTerminal && swift test`
    — 435 tests, 52 suites, all pass; `xcodebuild -project Corta.xcodeproj
    -scheme Corta -destination 'platform=macOS' build` — BUILD SUCCEEDED.
    Measurement (`swift run -c release corta-bench`, "write backpressure"):
    caller-side cost of a 1 MB write with a full pty buffer 43.5 ms before
    → 0.0 ms after (96 MB pre-fill 4327 ms → 0.0 ms); keypress→grid latency
    unchanged (p50 0.010 ms → 0.009–0.011 ms). Remaining limitation: a
    child that traps SIGHUP and never exits can keep one drain parked in
    `write(2)` past `stop()` (same pre-existing hazard class as the reader
    thread's blocking read; bounded by one chunk, never the caller).
- [x] P02 **inspection**: Measure lock wait during feed/reflow/snapshot; reduce
  long critical sections and publish consistent render state. Correct comments
  claiming the lock is never held across feed.
  - Fixed 2026-09-07. Measured with new `corta-bench` benchmarks
    ("snapshot latency under flood" + a same-run quiet control, sampled at
    `.userInteractive` — the render thread's QoS; the QoS matters: a
    lower-priority waiter loses the re-acquire race to the higher-priority
    reader at every boundary, which a default-QoS sampler shows as
    whole-batch starvation). Instrumentation showed the wait was *not*
    long critical sections — slice holds were p50 0.24 ms / max 2.5 ms —
    but starvation: releasing `os_unfair_lock` wakes a waiter, yet the
    reader's unlock→relock window (~ns between slices, ~tens of µs across
    an inter-batch read under flood) is shorter than a futex wake plus
    scheduling, so the waiter lost the race at every boundary (27/4682
    snapshot calls waited >10 ms, max ~490 ms). Fix in
    `TerminalSession.swift`: batches feed under the lock in 16 KB slices,
    and the reader leaves a real 100 µs gap between batches/slices whenever
    a render-path waiter is registered (`stateWaiters`, bumped by
    `snapshot()`, `isSynchronizedOutputEnabled` and the resize commit via
    `registerStateWaiter`; `yieldToStateWaiters` in the reader loop). The
    gap fires only while someone waits, so uncontended flood throughput is
    unaffected (one atomic read per boundary). The stale header comment
    claiming the lock is "never held across a parse batch" is corrected —
    feed is under the lock by design (grid single-threading + resize
    atomicity), sliced and gap-yielded instead. Measured after: snapshot
    under `yes` flood p99 0.000 ms / max 0.030–0.054 ms (before: p99
    1.3–42.8 ms, max 77–269 ms), control ~0; reflow critical section
    unchanged at ~99–205 ms for 100k-line scrollback (the P03 ordering
    contract requires the commit under the lock; documented). Regression:
    `TerminalSessionLockWaitTests.snapshotDoesNotStarveDuringAnOutputFlood`
    (500 snapshots mid-flood, per-call 100 ms starvation ceiling — verified
    red at 280 ms with the yield disabled). Verified: `cd CortaTerminal &&
    swift test` — 435 tests, 52 suites, all pass; `swift run -c release

  Implemented 2026-09-08. Three gaps, all closed.
  **(1) The arrangement was written only at `applicationWillTerminate`** —
  the one moment a crash never reaches. A restore exists for crashes, and the
  file was guaranteed stale in exactly that case. Layout changes are now
  written debounced (0.5 s) by `AppDelegate.noteLayoutChanged`, triggered by

  is also how a divider drag arrives). Flushed synchronously at quit, where
  waiting out the debounce would mean not writing at all; suppressed once the
  app is terminating so the windows closing on the way out do not write an
  empty arrangement over the one just flushed.
  **(2) The state file was deleted at launch** so a crash mid-restore could
  not replay forever — which also meant a crash at any *other* time lost the
  arrangement entirely. The two requirements are now separated by a marker
  file: `SessionRestore.beginRestore()` writes it, `endRestore()` removes it,
  and a launch that finds it left over knows the previous restore is what
  died and starts fresh. The state file itself is kept and kept current.
  **(3) Restored geometry and layout were trusted.** A state file is
  hand-editable and crash-truncatable. `WindowState.Frame.isUsable` rejects
  non-finite, negative and impossibly small frames *before* the on-screen
  clamp — `NaN` matters most, because `min`/`max` propagate it silently

  `NSWindow.setFrame` untouched. `PaneLayout.validated()` clamps divider
  fractions into `0.05...0.95` (a non-finite one becomes a centred split) and
  collapses nesting past 12 levels — 4096 panes — because `PaneLayout` is
  recursive and a truncated or hostile JSON nesting thousands deep would
  recurse the decoder and every walk over the tree until the stack ran out.
  Repaired rather than rejected: an arrangement with one silly divider is
  still the arrangement the person had.

  not the font stack.** Corta rasterises one glyph per cell — ASCII through

## Completion rules

The follow-up API/menu/CI review and additional findings are recorded in
[V0.1.1-ENGINEERING-AUDIT.md](V0.1.1-ENGINEERING-AUDIT.md). Keep both records
when breaking work into implementation milestones.

For each item record the change, tests/manual evidence, applicable baseline
and remaining limitations. Never mark it complete solely because it builds.
New product features are accepted backlog, not silent permission to remove
security constraints or expand into AI/cloud/multiplexer features. The final
0.1.1 release cut should explicitly identify any accepted work still pending;
do not silently discard it to meet a version number.
