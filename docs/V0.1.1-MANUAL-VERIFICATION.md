# 0.1.1 manual verification

Six checks that no automated run can stand in for, written to be worked
through in order by the maintainer on the release build. Each one says what
has to be true before you start, what to do, what counts as a pass, and what
to write down when it fails — a bug report with the third of those missing is
a bug report that gets reopened.

Tick a box only after the check passed as written. A ticked list is the
evidence; there is nothing else to file.

**The build under test.** Every check below is against a Release build, not
the Debug one:

```sh
xcodebuild -project Corta.xcodeproj -scheme Corta -configuration Release \
  -destination 'platform=macOS' build
open "$(bash scripts/find-release-app.sh)"
```

**A note on test fixtures.** Where a check needs a particular shell or
environment, pass it in the environment of the launch you control —
`SHELL=/path/to/script Corta.app/Contents/MacOS/Corta`. Never through
`launchctl setenv`, `defaults write`, or your shell's rc files: those outlive
the test and have already cost this project days once (`CLAUDE.md`, "Never
change the machine to test").

## 1. VoiceOver reads the terminal (U01)

Automated coverage asserts the coordinate and text mappings in isolation.
Whether VoiceOver actually speaks a screen of output, and whether its cursor
box lands on the character it is reading, is a thing you have to hear.

**Before you start**
- Release build running, one window, no splits.
- VoiceOver off. You will turn it on inside the app (⌘F5).
- A screen with real content: run `ls -la /usr/bin | head -40`.

**Steps**
1. ⌘F5 to start VoiceOver. Click once in the terminal view to focus it.
2. VO-A (Control-Option-A) to read the whole screen from the top.
3. VO-Right / VO-Left along one line, character by character.
4. VO-Down / VO-Up between lines.
5. Type `echo 中文测试と日本語` and Return, then read that line character by
   character.
6. Select `中文测试` with the mouse, then with ⇧-arrows from the keyboard.
7. Read the selection (VO-F6 twice, or VO-A over the selected range).

**Passes if**
- Every line of the forty is spoken, in order, with no line skipped and no
  line repeated.
- The VoiceOver cursor box sits over the character being spoken — including
  over the CJK characters, where the box must cover the whole two-column
  character and not half of it.
- Row and column announced for the cursor match where the caret actually is.
  Check at three positions: column 1, mid-line, and the last column.
- The CJK selection is read back as the characters you selected, not as
  bytes, replacement characters, or a longer or shorter run.

**If it fails, write down**
- The exact line of output being read, copied from the terminal.
- What VoiceOver said, verbatim, versus what is on screen.
- Where the cursor box was drawn — a screenshot with the box visible is worth
  more than a description.
- Whether the failure survives a restart of VoiceOver and of the app.
- macOS version, and whether the failing content was ASCII, CJK, emoji, or a
  combining sequence.

- [x] 1. VoiceOver — **2026-09-09, partial pass.** Verified from the caption
  panel and screenshots rather than by ear. The area announces "30 rows by
  120 columns. Cursor on row 30, column 29." against a prompt 28 characters
  wide on the last row of a 30-row grid — both coordinates correct. The
  VoiceOver cursor box over `中文` encloses both characters, four columns,
  with no half-character clipping, and the caption reads exactly `中文`:
  the wide-character rectangle fix (part of `531b0da`) confirmed against a
  real screen reader rather than only against `AccessibilityMappingTests`.
  **Not judged**: whether a forty-line read-through skips or repeats a line.
  That half is spoken, and the person running it could not follow spoken
  English closely enough to say. Reaching it would need someone who reads by
  ear, or the caption panel stepped line by line.

## 2. IME across window states (U02)

The preedit overlay's stale-metrics bug (U02) is fixed and covered, but the
candidate window is placed by the input method using the coordinates Corta
reports, and only a real IME can say whether they are right.

**Before you start**
- A CJK or Japanese input source installed and switchable (System Settings ▸
  Keyboard ▸ Text Input). Pinyin or Japanese Romaji both work.
- An external display connected, if you have one. If you do not, skip step 5
  and say so on the line below rather than ticking it.

**Steps** — in each of the six states, type `nihao` (or `nihongo`) without
committing, and look at where the candidate window is:
1. Single pane, default font size.
2. After ⌘= three times, then ⌘- three times back.
3. Split right (the Shell menu), typing in the *right* pane.
4. Split down as well, typing in the bottom pane.
5. Window dragged to the external display, then back.
6. Full screen (⌃⌘F).
7. After sleep: close the lid or ⌃⇧⏏, wake, then type again.

**Passes if**
- The candidate window's top-left corner sits directly under the preedit
  text, in every one of the states above, within roughly a character's width.
- The preedit text is drawn in the terminal at the cursor, underlined, and it
  moves as you type more syllables.
- Committing (Return or a candidate number) sends the committed characters
  once, and the preedit disappears.
- Escaping cancels the composition and sends nothing.

**If it fails, write down**
- Which of the seven states, and whether the previous state was entered
  first (the bug may be in the transition, not the state).
- The input source, by name.
- A screenshot showing the preedit and the candidate window together.
- Whether the offset is constant or grows with the number of characters
  typed — that difference tells the origin from the advance.

- [x] 2. IME placement — **2026-09-09, pass, after two defects were fixed.**
  The candidate window sits under the preedit at the default size, after
  three ⌘= and three ⌘-, in the right pane of a left/right split, in the
  bottom pane of a further split, and in fullscreen. External display and
  sleep/wake were not exercised.
  Two defects found by looking, neither of which any test here would have
  caught:
  - **The preedit was drawn in near-white on a light background** and could
    not be read. The overlay held its own copy of "the colour the renderer
    uses"; it reads the live palette now (`c4a3e82`). This is the second
    copy of an owned value found in that one view — U02 removed its stale
    cell metrics for the same reason.
  - **The text grew for the length of a window zoom** and shrank back
    afterwards. Three attempts: asking for a frame when the drawable
    resizes, then setting `contentsGravity` on the layer, then the property
    that actually governs it. For a layer-hosting view AppKit owns
    `contentsGravity` and derives it from `layerContentsPlacement`,
    overwriting a direct assignment — measured, and it is why the first two
    attempts changed nothing. The default,
    `.scaleAxesIndependently`, stretched the last presented frame over the
    whole animation. Reported as "basically gone" after the third fix
    (`80b7e84`), not as certainly gone.
  The comparison that pinned the second one was the reporter's: Terminal.app
  goes straight to the correct size, so it was not the system's animation.

## 3. A non-US keyboard, with and without option-as-meta (U05)

`option-as-meta` is covered by tests against synthesised events. What no test
here can produce is a dead key on a real layout, where the option key is how
you type an ordinary character rather than a modifier.

**Before you start**
- German or French added as an input source, and selected.
- Both settings to be tried: `option-as-meta = false` (the default) and
  `true`, changed in Settings ▸ Keyboard, or in `~/.config/corta/config`.
  Put the file back the way you found it when you are done.

**Steps** — run each pass with `cat > /dev/null` in the foreground so the
bytes are visible with `cat -v`, or just watch the shell's own echo:
1. With `option-as-meta = false`: type the layout's dead keys — on German,
   `´` then `e` for `é`; on French, `^` then `o` for `ô`.
2. Type the option-key characters the layout provides: German ⌥-l for `@`,
   ⌥-5 for `[`, ⌥-8 for `{`; French ⌥-5 for `[`.
3. Type `äöüß` (German) or `éèàç` (French) directly.
4. Now set `option-as-meta = true` and repeat 1-3.
5. In both passes, check ⌥-f and ⌥-b in a `zsh` prompt (move by word).

**Passes if**
- With `option-as-meta = false`: every character in steps 1-3 arrives exactly
  once, correctly composed. A dead key followed by a vowel produces the
  accented vowel, not two characters and not a beep.
- With `option-as-meta = true`: ⌥-f and ⌥-b move by word, and the trade-off is
  explicit — the option-key characters in step 2 are no longer reachable.
  That is the setting doing what it says, not a bug.
- Neither setting sends a partial or doubled character.

**If it fails, write down**
- Layout, setting value, and the exact keys pressed in order.
- The bytes received — run `cat -v` and copy what it printed.
- Whether the same keys behave correctly in Terminal.app on the same layout.

- [x] 3. Non-US layout, `option-as-meta = false` — **2026-09-09, pass.**
  German dead keys compose (`´` then `e` gives `é`), the layout's
  option-produced characters arrive, and the accented characters type
  directly.
- [x] 3. Non-US layout, `option-as-meta = true` — **2026-09-09, pass, after
  the setting was made to work at all.** ⌥F and ⌥B send `ESC f` and `ESC b`,
  confirmed by reading the bytes under `cat -v` rather than by inferring
  them from cursor movement — which is what the first attempt at this check
  did, and it was inconclusive because a forward-word at the end of a line
  correctly does nothing.
  **The setting had never worked.** `bytes(for:)` handled it from the day
  U05 landed, and the event never reached that function: an ⌥-only press
  carries neither ⌘ nor ⌃, so it was offered to the input context first,
  macOS composed the layout's alternate character, and it returned through
  `insertText`. ⌥F arrived as `ƒ`. Fixed in `3804c7b`; ⌥ now bypasses the
  IME when, and only when, the user has said ⌥ is Meta.
  The reason it shipped broken is worth more than the fix: the encoder had
  thorough unit tests and **the dispatch into it had none**, so a feature
  with passing tests was inert end to end. Both are covered now.

## 4. Copy-on-select, and whether the default is right (U08)

This is not a correctness check. `copy-on-select` is a habit question, and
the only way to answer it is to live with the setting for a working day and
notice what it costs.

**Before you start**
- Use Corta as your terminal for at least half a day with the default.
- Note the default's current value in `docs/CONFIGURATION.md` before you
  start so the comparison is against a recorded starting point.

**What to notice**
- How often a selection you made to *read* something overwrote a clipboard
  you were still using.
- How often you selected text and then reached for ⌘C anyway.
- Whether losing the clipboard to an accidental drag ever cost you real work.
- Whether the middle-click / paste-primary habit from X11 shows up here at
  all, or whether the macOS clipboard makes it moot.

**Passes if** — you can state the decision and the reason in one sentence,
whichever way it goes. "Keep the default" is a pass. "Change the default" is
a pass. "I did not notice" means it has not been used enough yet.

**Write down**
- The decision, and the sentence.
- Then make the record match: `docs/CONFIGURATION.md`'s row for
  `copy-on-select`, and the U08 entry in `docs/V0.1.1-QUALITY-PLAN.md`.

- [x] 4. `copy-on-select` default decided and recorded — **2026-09-09: keep
  the default.** Used through ordinary work; no clipboard was lost to a
  selection made only to read something, and nothing had to be re-copied.
  The decision is "no change", which is a result rather than an absence of
  one, and `docs/CONFIGURATION.md` already describes the shipped behaviour.

## 5. Keypress-to-pixel latency, in the fixed environment (Q07, and M9's debt)

The automated half of Q07 — memory, throughput — is done and recorded. Input
latency needs Typometer and a camera-free but carefully held environment,
which is a person's job.

`docs/PERFORMANCE.md` §5.2 defines the fixed benchmark environment. Hold all
of it; a number measured outside it is not comparable to M6.12's 45.5 ms, and
the M9 measurement's whole problem was that it was not held.

**Before you start**
- Release build, freshly launched, no other Corta windows.
- The §5.2 table satisfied item by item — display mode and refresh rate,
  power source and power mode, no other applications running, the same font
  size and window geometry.
- Typometer installed and configured as §5.2 describes.

**Steps**
1. Record the environment first: every row of §5.2's table, with the value
   you actually held it at, written down before the first measurement.
2. Measure Corta with the default configuration. Report average, and the
   spread across runs, not just the average.
3. Repeat the same measurement in the same session, without changing
   anything, to see the run-to-run spread of the harness itself.
4. **The M9 debt**: M9's 70.1 ms was measured in an environment that was not
   fully held, so it cannot be compared against M6.12's 45.5 ms. Re-measure
   M9's configuration here, in the environment you just recorded, so the two
   numbers finally mean the same thing.
5. Optional but valuable, and the only remaining half of Q07: the same
   Typometer measurement against Terminal.app and Ghostty on this machine, in
   this environment.

**Passes if**
- The environment table is filled in *before* the numbers, and every row
  matches §5.2.
- Corta's average is recorded with its spread.
- M9's configuration has a number measured in the same environment as the
  default configuration's, so the comparison against 45.5 ms is finally a
  comparison.

**If a number looks wrong, write down**
- The whole environment table as held, not just the row you suspect.
- Whether the app had been running long enough for the first-frame and font
  atlas costs to be out of the way.
- Whether anything else was on the display — a screen recorder, a video call
  and a browser all change this number.

**Then update**: `docs/PERFORMANCE.md` §5 with the new numbers, and
`docs/ROADMAP.md`'s M9 section, which currently flags exactly this gap.

- [x] 5a. Environment table recorded before measuring — **2026-09-09.**
  Every row of §5.2 collected before the first sample and written into
  `PERFORMANCE.md` §5: MacBook Air, Apple M5 (Mac17,3), macOS 26.6.2,
  Release at `12ac1b8`, built-in 60 Hz panel at native 2x, System Monospaced
  12 pt, 120×30 single pane, mains power, nothing else in the foreground,
  test program `cat > /dev/null`.
- [x] 5b. Corta default configuration measured, with spread — **2026-09-09:
  57.8 ms average, 45.3 ms min, 78.9 ms max, 5.6 ms SD** over 200 samples.
  Not the p50/p95/p99 §5.1 asks for: Typometer does not report percentiles,
  and the raw samples were not exported. Recorded as the limit it is.
- [x] 5c. M9's configuration re-measured in the same environment —
  **2026-09-09, same run.** M9's 70.1 ms was the *default* configuration
  measured without §5.2 held, so re-measuring the default properly is the
  re-measurement M9 owed; 5b and 5c are one run, not two.
  It does not make M9's number comparable retroactively — nothing can — but
  the configuration now has a figure taken in a recorded environment.
- [ ] 5d. (Optional) Terminal.app and Ghostty measured in the same
  environment — **not done.** Optional, and the comparison it would support
  is already partly covered by the throughput and memory measurements in
  Q07.

  **Two things this run exposed about the older numbers.** M6.12 recorded
  its Typometer settings and *not* its test program, and no run has ever
  recorded the machine beyond "MacBook Air, Apple silicon" — §5.2's own
  first row. So today's 57.8 ms sits 12.3 ms above 45.5 ms across at least
  one variable nobody wrote down. The fix is not to re-open M6.12; it is
  that this run's environment is recorded in full, so the next comparison
  is a real one.

  Getting the run to complete at all took two attempts, and the reason is
  worth keeping: typing into a live `zsh` prompt stalled Typometer at the
  character-deletion step — the shell's line editor redraws whole lines, so
  the screen change it waits for never arrived in the shape it expected.
  `cat > /dev/null` has the tty echo and no line editor, and it ran first
  try. §5.2 already required naming the test program; this is why.

## 6. IME under the comparison (Q07's other half)

The one part of the Q07 comparison that has no automated form at all: whether
composing in another language *feels* the same in Corta as in the terminals
people are coming from.

**Before you start**
- The same input source as check 2.
- Terminal.app and Ghostty open beside Corta, same font size, same window
  size.

**Steps** — in each of the three, compose the same sentence of CJK or
Japanese text, twenty or so characters, and switch candidates a few times.

**Passes if** — you can say, in a sentence, whether Corta is better, worse or
indistinguishable, and if worse, in what specific way: candidate placement,
lag between keystroke and preedit, flicker, or the commit itself.

**Write down** — the sentence, and the terminals' versions.

- [x] 6. IME compared, with a sentence — **2026-09-09: indistinguishable.**
  Composing the same Chinese sentence in Corta, Terminal.app and Ghostty
  side by side, at the same font and window size, the person doing the
  comparison could not tell them apart on candidate placement, lag to
  preedit, flicker, or the commit itself.
  There is no technical measurement to fall back on here, and that is not a
  gap in effort: measuring IME latency across applications needs
  instrumentation inside each one — available for Corta, not for the other
  two — or a high-speed camera. The check is perceptual by design, and
  "indistinguishable" is one of the three answers it asks for.

## When the list is finished

Everything above is a Stage 3 or Stage 4 item that says, in
`docs/V0.1.1-QUALITY-PLAN.md`, that its remaining half is a human judgement.
Close the loop in both directions:

- Tick the boxes here.
- Copy each result into that item's record — a sentence per item, in the
  place the record already reserves for it.
- If any check fails, the item goes back to `[ ]` there with the failure
  written out. A ticked box with a failed check underneath it is worse than
  no list.
